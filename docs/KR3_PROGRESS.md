Работа ведётся в существующей ветке `main`. Коммиты, push и merge выполняет
пользователь. Каждый следующий этап начинается только по его команде.

## Этап 0 — аудит

Изучены требования КР3, схема `database.sql`, тег КР1 `kr1-final`, JavaFX-клиент,
JDBC-репозитории, сервисы и тесты КР2. Полный аудит и план представлены в чате.
На этапе аудита исходники не изменялись.

## Этап 1 — каркас backend

Область: отдельный Maven-проект `backend/`, Java 21, Spring Boot, REST,
валидация, единая обработка ошибок, Swagger/OpenAPI, Actuator health,
контекстные и HTTP-тесты, инструкции запуска.

КР2 сохраняет собственные `pom.xml`, `src/` и способ запуска JavaFX.
Бизнес-сущности и схема БД на этапе 1 не изменяются. PostgreSQL, Flyway,
Hibernate, JWT, роли, frontend и Docker ещё не реализованы.

Общие файлы команды: `backend/pom.xml`, `backend/src/main/resources/application.yml`,
общая обработка ошибок и OpenAPI-конфигурация. У каждого должен быть один
ответственный. Проверки и документацию можно распределить отдельно от каркаса.

Критерии готовности: `mvn -f backend/pom.xml clean verify`, проверка запуска
исполняемого JAR и доступности `/api/v1`, `/actuator/health`, `/swagger-ui.html`,
`/v3/api-docs`; отдельная сборка КР2; сохранение пользовательских правок.

## Этап 3 — авторизация и сессии

Начальное состояние Git: чистая ветка `main`. Общие файлы этапа:
`backend/pom.xml`, конфигурация Security/OpenAPI, `application.yml`, обработчик
ошибок и новая миграция V4. Тестовые сценарии и документацию можно распределять
отдельно от реализации транзакций и правил доступа.

Реализовано:

- Spring Security Resource Server, JWT HS256 с обязательным внешним ключом,
  проверкой issuer/audience/назначения/времени и ограниченным TTL.
- BCrypt cost 12, политика паролей и отсутствие паролей/хешей в REST-ответах.
- Роли VIEWER/MANAGER/ADMIN, правила просмотра, редактирования и административных
  действий. Для будущих CRUD-контроллеров задана URL-политика; сами CRUD ещё не реализованы.
- Вход, refresh с ротацией, logout, текущий пользователь и смена пароля.
- Случайный refresh: только SHA-256-хеш в БД, фиксированный срок семейства,
  отзыв всего семейства при повторе старого токена. V4 добавляет `family_id`.
- Проверка актуальной сессии и роли в БД для access: отзыв сессии, блокировка и
  смена роли действуют сразу. Смена пароля отзывает все прежние сессии пользователя.
- Обязательная смена временного пароля: до неё бизнес-доступ закрыт.
- Персистентный счётчик попыток и временная блокировка входа с advisory-блокировкой
  для параллельных запросов; общая ошибка для неизвестного/отключённого пользователя
  и неверного пароля.
- Явный bootstrap первого администратора из окружения, без стандартного пароля
  и без сброса существующих учётных данных при повторном запуске.
- Общие безопасные ошибки 400/401/403/429, `no-store`, скрытые `toString()` секретных
  DTO и проверка секретных полей без rejectedValue в исключениях валидации.
- Swagger Bearer Authorize, `.env.example`, инструкция `backend/docs/AUTH.md`.

## Этап 5 — автомобили и справочники

Начальное состояние Git: чистая ветка `main`. Общие файлы: VersionedEntity,
обработчик ошибок, типы аудита и контракты DTO. Автомобили и справочники можно
распределять отдельно после согласования ссылок и правил включения. Новых
миграций и зависимостей не потребовалось; схема этапа 2 уже содержит нужные поля.

Реализовано:

- REST-чтение списка/одной записи, создание и полное изменение автомобилей по
  публичному UUID; DTO без внутренних ключей автомобиля и учётных данных продавца.
- Выбор продавца по ID/ФИО включённых профилей, справочники по ID; марка выводится
  из модели. Основные правила КР2 сохранены: цена, пробег, год, объём двигателя и VIN.
- Нормализация внешнего кода, VIN и тегов; уникальность кода/VIN проверяется в
  сервисе и БД. Архивный признак и серверные поля не принимаются в теле записи.
- Вычисляемый возраст `max(0, текущий год − год выпуска)` через Clock.
- Пять справочников: список/одна запись, создание, переименование, включение и
  отключение без удаления. Модели выбираются по марке; перепривязка существующей
  модели к другой марке запрещена, чтобы не изменить все связанные автомобили.
- Версии обязательны при изменении, устаревшие дают 409. Строка блокируется до
  проверки, а flush перед ответом выдаёт новую версию. Изменение только характеристик
  или тегов помечает автомобиль через touch и также увеличивает его версию.
- Новое назначение отключённого справочника/продавца запрещено; неизменённая старая
  связь сохраняется при редактировании. Эффективная доступность модели учитывает марку.
- CREATED/UPDATED подключены к транзакционному аудиту. Идентичные PUT/PATCH без
  изменений не увеличивают версию и не создают событие.
- Обработаны 400/404/409 без SQL во внешнем ответе, права защищены URL-политикой
  и method security пишущих сервисов. Документация: `backend/docs/CARS.md`.
