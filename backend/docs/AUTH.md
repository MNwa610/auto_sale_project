# Авторизация — этап 3 КР3

Spring Security проверяет JWT HS256. Access передаётся в `Authorization: Bearer
<accessToken>`. Refresh — отдельная случайная строка из 32 криптографически
случайных байт (Base64URL без padding). В БД refresh хранится только как SHA-256-хеш.
Пароли хешируются BCrypt с cost 12.

## Настройка и первый администратор

Обязательный `JWT_SECRET_BASE64` — Base64 от минимум 32 случайных байт.
Сгенерировать локально: `openssl rand -base64 32`. Сохранить результат в локальном
окружении или игнорируемом `.env`, не в Git. `.env.example` содержит текст для
замены, а не действующий ключ. Между перезапусками ключ надо сохранять, иначе
старые access перестанут проходить проверку подписи.

По умолчанию access живёт 10 минут, refresh-семейство — 7 дней от момента входа.
Параметры `carmarket.auth.*` находятся в `application.yml`; стандартное
переопределение Spring: например `CARMARKET_AUTH_ACCESS_TTL=PT5M`. Допустимый access
TTL — 1–15 минут, refresh TTL — 1 час–30 дней.

Автоматическое создание администратора по умолчанию выключено. Для первого входа
задайте `BOOTSTRAP_ADMIN_ENABLED=true`, `BOOTSTRAP_ADMIN_LOGIN` и свой временный
`BOOTSTRAP_ADMIN_PASSWORD`, затем запустите backend обычной командой.
Пароль должен соответствовать политике ниже. Универсального пароля нет.

При наличии активного администратора с хешем повторный bootstrap ничего не
меняет. Если логин занят, а активного администратора нет, запуск отклоняется:
выберите новый логин. Созданный аккаунт обязан сменить пароль при первом входе.
После создания отключите bootstrap и удалите временный пароль из окружения/`.env`.
Обычный запуск требует только пароль БД и ключ JWT.

Перенесённые аккаунты КР1 остаются заблокированными. Bootstrap может создать нового
администратора с незанятым логином. Безопасное включение старых пользователей и
управление ими относятся к этапу 11; публичной регистрации и произвольного
сброса чужого пароля сейчас нет.

## REST-контракт

`POST /api/v1/auth/login` — тело `{"login":"<логин>","password":"<пароль>"}`.
Успешный ответ: `accessToken`, `refreshToken`, `tokenType` (`Bearer`),
`expiresInSeconds`, `refreshExpiresAt`, `user` (`id`, `login`, `fullName`, `role`,
`mustChangePassword`). Пароли и хеши не возвращаются. Ответы имеют
`Cache-Control: no-store`.

`GET /api/v1/auth/me` — текущий пользователь, требуется access.

`POST /api/v1/auth/refresh` — тело `{"refreshToken":"<текущий refresh>"}`.
Возвращает новую пару. Старый refresh отзывается; срок семейства не продлевается.
Старый access после ротации также не принимается. Если семейство истекает раньше
обычного access, срок access сокращается до конца семейства.

Повторное использование отозванного refresh отзывает всё его семейство, включая
дочерние сессии. Клиент должен выполнять только одно обновление одновременно и
атомарно заменять пару токенов. При параллельном обновлении один запрос может
вернуть 200, а повторный отзовёт и эту пару; после этого нужен новый вход.

`POST /api/v1/auth/logout` — то же тело, что у refresh; отзывает семейство и
возвращает 204. Повторный выход или неизвестный токен корректного формата также
дают 204. Другие устройства не затрагиваются. Access для выхода не нужен;
не добавляйте истёкший access в Authorization этого запроса.

`POST /api/v1/auth/password` — требуется access, тело:

```json
{"currentPassword":"<текущий пароль>","newPassword":"<новый пароль>"}
```

Текущий пароль должен быть правильным, новый — отличаться от него. Смена отзывает
все прежние сессии на всех устройствах и снимает `mustChangePassword`. В ответ
возвращается новая пара токенов.

Swagger UI `/swagger-ui.html` поддерживает Authorize с access JWT.

## Пароли, права и сессии

Новый пароль: минимум 12 Unicode-символов, заглавная и строчная буква, цифра;
максимум 72 байта UTF-8 из-за ограничения BCrypt. Пароль не обрезается и не
нормализуется. Логин приводится к нижнему регистру, крайние пробелы удаляются.

При временном пароле доступны профиль, refresh, выход и смена пароля, а также
публичные служебные endpoint. Бизнес-запросы дают 403 `PASSWORD_CHANGE_REQUIRED`.

- `VIEWER` — чтение бизнес-данных.
- `MANAGER` — чтение и изменение бизнес-данных.
- `ADMIN` — также изменение справочников, пользователи, аудит, окончательное удаление автомобилей.

URL-правила подготовлены для будущих контроллеров. Автомобильный и административный
CRUD ещё не реализован. Контроллеры проверки ролей находятся только в тестах и
не входят в JAR.

Проверяются подпись HS256, issuer, audience `carmarket-api`, срок и назначение
`token_use=access`. Затем сервер читает актуальную сессию, блокировку аккаунта,
роль и флаг временного пароля из PostgreSQL. Роль из JWT не заменяет роль БД:
отзыв и блокировка прекращают доступ сразу, без ожидания истечения access.

HTTP-сессии и cookie-аутентификация не используются. CSRF отключён для Bearer API
с refresh в JSON-теле; переход к cookie потребует отдельной настройки CSRF.

## Попытки входа и ошибки

Пять неверных попыток по нормализованному логину в окне 15 минут блокируют вход
на 15 минут (429). После истечения блокировки счётчик начинается заново; успешный
вход его очищает. Лимиты настраиваются в `carmarket.auth.*`. Счётчик хранится в БД
под транзакционной advisory-блокировкой, включая несуществующие логины. Параллельные
запросы и разные экземпляры backend не теряют попытки.

Неверный пароль, неизвестный логин и отключённый аккаунт возвращают одинаковую
ошибку. Для отсутствующего пароля проверяется фиктивный BCrypt-хеш.

Ошибки сервисов авторизации и фильтров: `application/problem+json`, поле `code`:

- 400: `INVALID_REQUEST`, `PASSWORD_POLICY`, `PASSWORD_REUSE`.
- 401: `INVALID_CREDENTIALS`, `INVALID_TOKEN`, `UNAUTHORIZED`.
- 403: `FORBIDDEN`, `PASSWORD_CHANGE_REQUIRED`.
- 429: `LOGIN_LOCKED`.

Общие ошибки разбора JSON и валидации несекретных полей сохраняют формат этапа 1
и могут не содержать `code`.

Секретные поля проверяются без исходного значения в исключении; их `toString()`
скрыт. Не включайте логирование полных HTTP-тел и Authorization во внешнем прокси.

`mvn verify` проверяет JWT, роли, смену пароля, ротацию/отзыв, блокировку,
bootstrap и конкурентные запросы на одноразовой PostgreSQL. Истечение проверяется
управляемыми часами без реального ожидания минут/дней.
Основа JWT-интеграции — [Spring Security 6.5 Resource Server](https://docs.spring.io/spring-security/reference/6.5/servlet/oauth2/resource-server/jwt.html).
