# Автомобили и справочники — этап 5

Все маршруты требуют access JWT и завершённой смены временного пароля.
VIEWER читает данные, MANAGER/ADMIN создают и изменяют автомобили.
Справочники изменяет только ADMIN. Сущности JPA не выдаются напрямую: API использует DTO.

## Автомобили

- `GET /api/v1/cars` — текущий полный список, включая архивные записи, по внутреннему
  порядку создания (ID). Ответ — массив DTO. Поиск, фильтры, сортировка и серверная
  пагинация относятся к этапу 6; этот массив пока не является страничным контрактом.
- `GET /api/v1/cars/{id}` — одна запись по публичному UUID, отсутствие — 404.
- `POST /api/v1/cars` — создание, ответ 201, DTO и Location новой записи.
- `PUT /api/v1/cars/{id}` — полное изменение с обязательным `version`, ответ 200.
- `GET /api/v1/cars/sellers` — доступные продавцы: только ID и ФИО включённых
  профилей, без логинов, ролей, паролей и хешей. Это выбор бизнес-связи, не API
  административного управления пользователями.

В ответе `id` — UUID; внутренний числовой ID автомобиля не публикуется. Справочники
выдаются как `{id,name,enabled}`, продавец — `{id,fullName}`. Есть статус,
`certified`, теги, `archived`, `version`, даты и вычисляемый `ageYears`.
У модели `enabled` в ссылке учитывает также состояние марки.

Пример тела создания (ID продавца/справочников заменить реальными значениями):

```json
{
  "externalCode": "AUTO-001",
  "sellerId": 1,
  "modelId": 1,
  "year": 2020,
  "mileage": 50000,
  "price": 1500000.00,
  "vin": "XTA12345678901234",
  "bodyTypeId": 1,
  "transmissionId": 1,
  "fuelTypeId": 1,
  "engineVolume": 2.0,
  "description": "Автомобиль после проверки",
  "status": "AVAILABLE",
  "certified": true,
  "tags": ["проверен", "акция"]
}
```

Для PUT передаются все те же поля и `version` из последнего ответа. При POST
`version` отсутствует, значение назначает сервер. UUID, даты и архивный признак
не принимаются в запросах записи. Марка выводится из `modelId`, отдельно передать
противоречащую марку нельзя. Статусы: AVAILABLE, RESERVED, SOLD.

Проверки продолжают правила КР2: цена > 0, до 10 целых и 2 дробных знаков; пробег
неотрицательный; год 1950–следующий модельный год, но не выше 2100; двигатель > 0,
до 99.9 с одним дробным знаком. Числа передаются JSON-числами с точкой.
VIN необязателен: пустое значение становится NULL, заполненный приводится к
верхнему регистру и должен иметь 17 латинских букв/цифр. Описание — до 4000 символов.

`externalCode` обрезается по краям, до 64 символов, уникален с учётом регистра.
VIN уникален после нормализации. Теги — до 20 элементов, каждый до 50 символов;
крайние пробелы удаляются, регистр понижается, повторы схлопываются. Пустые теги
и управляющие символы отклоняются.

Возраст: `max(0, текущий год по Clock backend − year)`. Для следующего модельного
года получается 0. Значение не хранится в БД и не принимается от клиента.

## Справочники

`{kind}` — фиксированный список: `brands`, `models`, `body-types`, `transmissions`,
`fuel-types`. Неизвестный вид даёт 404, пользовательское значение не становится SQL.

- `GET /api/v1/catalogs/{kind}` — все записи, включая отключённые, по названию и ID.
- `GET /api/v1/catalogs/models?brandId=1` — модели выбранной марки; `brandId`
  допустим только для списка моделей.
- `GET /api/v1/catalogs/{kind}/{id}` — одна запись.
- `POST /api/v1/catalogs/{kind}` — создание (201 и Location).
- `PUT /api/v1/catalogs/{kind}/{id}` — название и состояние с проверкой версии.
- `PATCH /api/v1/catalogs/{kind}/{id}/enabled` — включение/отключение с версией.

Пример создания марки: `{"name":"Lada","enabled":true}`.
Пример создания модели: `{"name":"Vesta","brandId":1,"enabled":true}`.
PUT дополнительно требует `version`; для модели также нужен прежний `brandId`.
Перенос существующей модели к другой марке запрещён: нужно создать новую модель,
чтобы незаметно не изменить марку всех связанных автомобилей.

Пример PATCH: `{"enabled":false,"version":0}`.
Ответ содержит `enabled`, `effectiveEnabled`, `version`, даты; у модели — `brandId`.
`effectiveEnabled` модели равен её enabled AND enabled марки. Отключение марки не
переписывает флаги её моделей. Вновь включить отключённую модель под выключенной
маркой нельзя. Имена уникальны без учёта регистра и крайних пробелов (модели —
в пределах марки). Лимиты названий: марка 50, модель 100, остальные 30 символов.

Отключённые записи физически не удаляются. Их нельзя заново назначить автомобилю,
но при редактировании можно сохранить неизменённую старую связь. Это относится и
к отключённому продавцу: профиль сохраняется в старой записи. Новое назначение
требует включённого профиля. Старые связи читаются вместе с актуальными названиями
справочников. Переименование справочника меняет отображаемое название, но не
ссылку или версию самого автомобиля.

## Конкурентные изменения и аудит

Изменение блокирует текущую запись, проверяет присланный version и сохраняет
новый JPA `@Version`. Равенство версии обязательно, даже если желаемое содержимое
совпадает с уже сохранённым. Характеристики и теги тоже увеличивают версию
автомобиля. Перед формированием ответа выполняется flush, поэтому новая версия
попадает в ответ. Полностью идентичный PUT/PATCH не увеличивает версию и не пишет
лишнее событие.

Проверки уникальности есть в сервисах и в PostgreSQL: параллельное создание с
одним внешним кодом не создаёт дубль. Чтение выбранных справочников блокируется
в пишущей транзакции от конкурентного отключения.

CREATED/UPDATED записываются в аудит в той же транзакции. Объект автомобиля —
UUID, объект справочника — тип и числовой ID. Для изменения сохраняются имена
изменённых полей, без копирования содержимого описания или целых DTO.

Ошибки имеют общий формат ProblemDetail: 400 — неверные поля/версия, 404 — нет
записи, 409 VERSION_CONFLICT — устаревшая версия, INACTIVE_CATALOG/INACTIVE_SELLER —
недоступная новая связь, ARCHIVED_CAR — попытка изменения архивной записи.
Дубли дают 409 (DUPLICATE_RECORD при предварительной проверке либо
DUPLICATE_OR_RELATED_RECORD при конфликте ограничения БД). SQL и его параметры
в ответ не попадают.

Архивирование, восстановление и окончательное удаление — этап 7. На этапе 5
DELETE автомобилей/справочников не реализован; изменение архивного автомобиля
запрещено, чтение доступно. Полное управление пользователями — этап 11.

## Проверки

`mvn verify` проверяет реальные контроллеры, сервисы, JPA и PostgreSQL. CRUD-тесты
используют тестовые аутентифицированные SessionUser для проверки ролей и аудита;
отдельные Auth API тесты продолжают проверять настоящие JWT и сессии. Есть проверки
характеристик/тегов, отключённых связей, идентичного PUT, двух одновременных записей
с одной версией и параллельного создания с одним внешним кодом. Возраст отдельно
проверяется на границе нового года и для будущего модельного года.
