# Аудит — этап 4

`AuditService` записывает событие в текущей бизнес-транзакции (`Propagation.MANDATORY`).
Без транзакции вызов отклоняется. Нет самостоятельной транзакции, асинхронной
записи или записи после commit. Ошибка аудита отменяет изменение; ошибка после
записи отменяет и изменение, и событие.

Событие содержит действие, тип и ID объекта, `actor_id`, снимок `actor_login`,
JSON-метаданные и время UTC из общего `Clock`. Миграция V5 добавляет снимок логина
и проверку JSON-объекта. После удаления автора FK становится NULL, снимок остаётся.
Старые события не переписываются. FK на целевой объект отсутствует: удаление
автомобиля не удаляет историю.

## Вызов из транзакционного сервиса

- `recordAsCurrentUser` получает `SessionUser` из SecurityContext. Без пользователя
  вызов отклоняется, автоматической подмены на SYSTEM нет.
- `recordAsUser` — внутренний вызов после проверки credentials, например при входе.
  ID автора нельзя брать из непроверенного HTTP-запроса.
- `recordSystem` — явная системная операция без придуманного пользователя.

Пример в будущей транзакции изменения автомобиля:

```java
audit.recordAsCurrentUser(AuditAction.UPDATED,
        AuditTarget.car(car.getPublicId()), AuditDetails.none());
```

`AuditTarget` принимает только числовой ID пользователя или UUID автомобиля/сессии.
`AuditDetails` принимает только enum имён полей, роль, флаг временного пароля и
число отозванных записей сессий. Произвольные строки, карты, тела запросов и
сущности не принимаются. Новые безопасные поля и типы добавляются на своих этапах.
PASSWORD обозначает только факт смены: значений паролей, хешей, ключей и токенов нет.
Не перехватывайте ошибку аудита для продолжения изменения. Репозиторий используется
только сервисом, напрямую вызывать его не следует.

## Подключённые события

- BOOTSTRAP_ADMIN_CREATED — системное создание первого администратора.
- LOGIN_SUCCEEDED — успешный вход, автор подтверждён проверкой credentials.
- PASSWORD_CHANGED — смена пароля и количество отозванных старых сессий.
- REFRESH_ROTATED — успешная ротация, цель — прежняя сессия.
- LOGOUT — фактический отзыв семейства, автор определён по refresh-сессии.
- REFRESH_REUSE_DETECTED — системный отзыв оставшихся сессий при повторе старого
  токена. Автор запроса неизвестен, событие не приписывается владельцу аккаунта.

Повторный bootstrap/выход без изменения состояния не создаёт событие. Replay,
которому уже нечего отзывать, тоже не добавляет запись. При ответе 401 на replay
отзыв и аудит намеренно сохраняются (`noRollbackFor=AuthFailure`, этап 3).
Неудачные входы остаются в `login_attempts`, не записываются как успешные действия.

На этапе 5 CREATED/UPDATED подключены к автомобилям и справочникам. Тип цели
включает пять справочников, метаданные — имена их полей и полей автомобиля.
Массовые операции, архивирование, удаление и CSV API ещё не реализованы. Существующий
перенос КР1 сохраняет системные события KR1_IMPORT вместе с переносом.

Приложение предоставляет только добавление событий; это не защита от изменений
администратором PostgreSQL. REST-просмотр с фильтрами/сортировкой относится к этапу 10.

Тесты проверяют commit/rollback данных и события, реальный отказ INSERT, запрет
вызова без транзакции, rollback при перехваченной ошибке, источник автора,
снимок после удаления и отсутствие секретов в событиях Auth API.
Основа: [транзакции Spring Framework](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html).
