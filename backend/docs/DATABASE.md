# База данных КР3

КР3 продолжает структуру КР1: `roles`, `users`, `user_credentials`, `brands`,
`car_models`, `body_types`, `transmissions`, `fuel_types`, `cars`,
`car_specifications`, `purchase_requests`. База КР3 отдельная; JDBC-записи
JavaFX не обходят её будущую авторизацию, аудит и контроль версии.

## Схема и модель

Внутренние PK остаются `BIGSERIAL`, связи используют `BIGINT`. Автомобиль
дополнительно имеет уникальный неизменяемый `public_id UUID`: будущий REST API
должен использовать его как идентификатор. `external_code` — отдельный
обязательный уникальный код для CSV; VIN остаётся необязательным.

Архив `archived` независим от статуса `AVAILABLE`, `RESERVED`, `SOLD`.
`certified` означает прохождение проверки автосалона; `car_tags` хранит набор
нормализованных тегов без повторов. Цена — `NUMERIC(12,2)`, пробег — целое
число километров. Возраст автомобиля планируется вычислять на backend на
этапе CRUD, он не хранится как устаревающая колонка.

В справочниках есть `enabled` для отключения без удаления. В сущностях с
изменяемыми данными есть `version`, `created_at`, `updated_at`.
JPA `@Version` защищает обновления от потери изменений. Будущий сервис CRUD
обязан сравнивать входную версию; при изменении только зависимых характеристик
он также должен увеличивать версию автомобиля (например, через принудительную
оптимистическую блокировку). Один `@Version` в родительской записи этого не делает.

Время хранится как `TIMESTAMPTZ`, Java использует `Instant`, JDBC — UTC.
В обычных JPA-записях временные метки обновляются callback-методами.
Произвольный внешний SQL обязан обновлять даты и версии самостоятельно.

Дополнительные таблицы: `refresh_sessions`, `login_attempts`, `car_notes`,
`audit_events`, `csv_import_sessions`. На этапе 2 это только структуры для
будущих модулей. Хеш refresh-токена хранится отдельно от будущего исходного
токена. Аудит не имеет FK на автомобиль, поэтому переживает его удаление.

Flyway — единственный механизм создания схемы. `clean-disabled=true`,
`baseline-on-migrate=false`, Hibernate — `validate`, SQL init — `never`.
Применённые миграции нельзя переписывать; изменения оформляются новой версией.

## Явный перенос из КР1

Сначала создать БД КР3 и один раз запустить backend, чтобы Flyway применил
`V1`–`V3`, затем остановить backend. Назначение должно содержать только роли
и историю Flyway. Инструмент откажется работать с непустыми таблицами данных.
Перед переносом сделайте резервную копию исходной БД и проверьте перенос на копии.

Нужны Python 3 и утилита `psql` в `PATH`. Переменные источника:

```bash
export KR1_PGHOST=localhost
export KR1_PGPORT=5432
export KR1_PGDATABASE=auto_sale
export KR1_PGUSER=postgres
export KR1_TIMEZONE=Europe/Moscow
```

Переменные назначения:

```bash
export KR3_PGHOST=localhost
export KR3_PGPORT=5432
export KR3_PGDATABASE=auto_sale_kr3
export KR3_PGUSER=carmarket
```

Также задайте `KR1_PGPASSWORD` и `KR3_PGPASSWORD` в окружении своей оболочки,
не сохраняя реальные значения в Git. Для TLS поддерживаются `KR1_PGSSLMODE`
и `KR3_PGSSLMODE`. Настройки `DB_*` backend не заменяют эти отдельные настройки
переноса. Инструмент не наследует случайные переменные `PG*` рабочего окружения.

Из каталога `backend`:

```bash
python3 tools/import_kr1.py --apply
```

Источник читается в согласованном read-only снимке. В назначении вставки
выполняются одной транзакцией с блокировкой таблиц от параллельных записей.
Нарушение ограничения или несовпадение количества строк отменяет вставки.
Данные передаются в памяти как JSON, пароли в командную строку не передаются.
Для больших производственных объёмов этот учебный инструмент не предназначен.

Правила преобразования:

- Числовые id пользователей, справочников, автомобилей, характеристик и заявок
  сохраняются. Последовательности продолжаются после максимального id.
- Роли сопоставляются по коду: `USER → VIEWER`, `ADMIN → ADMIN`, их числовые id
  не копируются. Неизвестные роли отклоняются.
- Автомобиль получает новый UUID и внешний код `KR1-<старый id>`.
- `ARCHIVED → archived=true, status=AVAILABLE`. Это техническое начальное
  значение: прежний коммерческий статус неизвестен. Перед восстановлением
  такого автомобиля менеджер должен подтвердить его актуальный статус.
- Исходный статус и id каждого автомобиля сохраняются в событии `KR1_IMPORT`.
- Старые пароли не выбираются из источника и не копируются. Учётные записи
  получают `enabled=false`, `must_change_password=true`, `password_hash=NULL`.
  Включать их можно только после безопасного задания пароля на этапе авторизации.
  Ненулевой пароль в БД должен соответствовать формату BCrypt.
- Логины приводятся к нижнему регистру с удалением крайних пробелов; коллизии
  отклоняются. VIN нормализуется в верхний регистр. Остальные некорректные
  значения не исправляются молча, а отклоняются ограничениями PostgreSQL.
- Наивные даты КР1 интерпретируются в `KR1_TIMEZONE` (по умолчанию Europe/Moscow).
  При иной зоне источника её надо указать явно.

Повторный перенос в заполненное назначение запрещён. Это отдельный перенос КР1,
а не будущий пользовательский CSV-импорт и не реализация API аудита.

## Воспроизводимая проверка переноса

После сборки JAR, из каталога `backend`:

```bash
python3 tools/test_import_kr1.py
```

При необходимости Java выбирается аргументом `--java /путь/к/java`.
Нужны Docker, Python 3 и `psql`. Проверка создаёт собственный контейнер PostgreSQL
16 с одноразовым случайным паролем и портом только на `127.0.0.1`, создаёт в нём
две тестовые БД, а по завершении останавливает и удаляет свой контейнер.

Скрипт КР1 `database.sql` выполняется исключительно в новой тестовой БД
`kr1_fixture` этого контейнера. Проверяются успешный перенос, неизменность
источника, откат при коллизии логинов, отказ повторного импорта, преобразование
архива, исключение паролей, продолжение последовательностей и повторный запуск
backend. Затем тест намеренно переименовывает колонку в одноразовой БД КР3
и проверяет, что Hibernate останавливает запуск, не исправляя схему.
